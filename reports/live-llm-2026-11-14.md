# Phase 3 — a live language model in front of the knowledge-based planting workflow (2026-11-14, M62)

Branch `feature/live-llm-interpretation`, cut from `design/studio-integration` (dffbf57). Not merged to `main`.

**State in one paragraph.** The interface to a real model is built, wired to Pages 1–3 and Grow, and tested end to end
through the real anthropic SDK. **The real model itself has not been called: this machine has no model credential**
(no `ANTHROPIC_API_KEY`, no `.env`, no CLI profile). Everything marked *mock* below is a hand-written answer sent through
the real code path; it tests the pipeline and its checks and says nothing about how well a model reads. With a key in
place the same commands produce the live column.

## What was built

```
words (Page 1 composer · Shape command bar · Compose command bar · Grow command bar)
  └─ app.js handleSay
       ├─ POST /api/interpret ──► tools/design_server.py ──► tools/llm_interpret.py
       │                             Claude API, structured JSON output (one schema)
       │                             1 schema check   2 grounding + business rules   3 offline parser's shapes
       │                          ◄── {mode: live | mock, result, validation}   or   {mode: offline, reason}
       └─ offline: design/js/intent.js (the rules)          ◄── no server, no key, a failure, a rejected answer
  both ─► the same applyDescription / bedEditPreview / edit preview
       ─► site model (model.js) ─► spatial engine (spatial.js) ─► knowledge adapter (knowledge.js) ─► planting engine (engine.js) ─► evaluation
```

- **Reused, not rebuilt.** The endpoint that was reserved in `tools/design_server.py` is now the real one; the model code
  moved to `tools/llm_interpret.py`. The page had never called it — and its top bar said "live model" whenever a key was
  present. Both are fixed. No second AI system, no new database, no vector store, no training.
- **The model reads language only.** One schema: kind (`description` | `bed_edit` | `edit` | `none`), site facts
  (size, trees, open areas, conditions), relationships, goals, spatial functions (the knowledge graph's five ids, with its
  definitions in the instructions), constraints, unknowns, and for every item the words it rests on. The schema has no
  field for a coordinate, a polygon, a plant fact or a plant choice.
- **Checked before use** (`llm_interpret.check`). Schema (types, enums, ranges, no extra key), then rules; what fails is
  dropped or corrected and listed:
  - every item must quote the utterance;
  - a size, a screen height, an amount must be a number the person typed (digits or "half a metre"); feet are converted
    by the workspace;
  - a compass side or corner needs the word that names it ("back / rear" = north, "front" = south, as in the rules;
    "left / right / behind" name no side for the site) — otherwise the edge is left unset and asked for, the tree waits
    unplaced;
  - a condition must be a value the site model records for that condition;
  - a bed edit is a typed request (which bed · operation · amount); the spatial engine computes, clips and previews it;
  - a planting edit names plants in the person's words; they are resolved against the ten species or not used.
- **Completed by the same rules as offline** (`intent.js completeBrief`, `groundCoverFromValues`, shared): standing
  constraints, what is still unknown, Screen from privacy, Scrim as the alternative, Ground Cover from the goals.
- **Live / Offline, said truthfully.** `/api/status` reports `live`, `mock` or `offline`. The top-bar tag shows what read
  the *last* sentence: `Live LLM · model`, `Offline rules`, `Offline rules · live model not used` (with the reason), or
  `MOCK model · test`. Every reply carries the same line, the model's one-sentence reading, the relationships it relied
  on, what the workspace's rules added, and a "Checked before use" list. Readings are kept in `project.interpretations`.
- **The key stays on the server.** Environment or a git-ignored `.env`; not in `/api/status`, not in any response, not in
  the repository; files whose name starts with a dot are no longer served. GitHub Pages has no API, so the page there
  reads with the rules (tested against a plain static server).
- **API details.** `claude-opus-5-5`, structured output (`output_config.format`), effort `medium`, 16 000 max tokens,
  60 s timeout, one retry, refusal fallback requested (`fallbacks: "default"`, with a plain retry where that beta is not
  offered). One bug in the reserved code would have broken every live call: its schema used `minimum` / `maximum`, which
  structured outputs reject; those are now stripped from the schema that is sent and checked on the server instead.

## How to run

```bash
python3 -m venv .venv && .venv/bin/pip install anthropic      # once; .venv is git-ignored
cp .env.example .env                                           # put ANTHROPIC_API_KEY in it (never committed)
.venv/bin/python -I tools/design_server.py --port 8770         # then http://127.0.0.1:8770/design/?fresh=1
.venv/bin/python tools/llm_tests.py                            # contract tests; runs the live block when a key is present
```

`?interp=offline` forces the rules on a server that has a model. Without a key the server and the page work as before.

## Knowledge retrieval and the planting engine were really called

Counted during the run by wrapping the knowledge adapter (`knowledge.js`): `gate` 235 calls, `functionEvidence` 215,
`heightAgainst` 45, `yearRound` 40, `sizeProxy` 469, `functionLink` 1 267. For the north bed `E.assemble` returned all
ten species classed for Screen against the requirement read from words (2 m, year-round) and the conditions the gates
read (light part-shade; water, soil unknown):

| species | fit | first reason | claims |
|---|---|---|---|
| *Gaultheria shallon* | uncertain | site gates unknown (water, soil); 2 of 3 claimed height ranges for shade reach 2 m | 6 (e.g. `gaultheria-shallon:mature_height:rhs01`), not all verified |
| *Cornus sericea* | fails | Screen derived from a recorded use (KG-R1, claims unverified) but a trait claim contradicts it; deciduous; its row needs 1.91 m of depth, the bed has 0.9 m | 8 |
| *Vaccinium ovatum* | fails | Screen derived from a recorded use (KG-R1, claims verified) but a trait claim contradicts it; its row needs 0.95 m of depth, the bed has 0.9 m | 8 |
| *Acer palmatum* | fails | a tree (no tree-placement rule); recorded deciduous; its row needs 3.97 m of depth | 8 |
| *Cercidiphyllum japonicum* | fails | Screen only inferred from traits (KG-R4) | 5 |
| five others | fails | no Screen link in the knowledge graph | 0 |

Pick: *Gaultheria shallon* (fit uncertain, gate unknown). Generated screen: **not met** (continuity not met, target
height uncertain, year-round met, evidence supported; 4.27 of 6 m covered), `verified_performance: false` everywhere.
The reader changed none of this: it supplied "2 m, year-round, part shade"; the database and the engine did the rest.

| **D** "make the bed along the north fence half a metre deeper, but don't let it eat into the open centre and keep the tree bed" | **read as a description — no bed changes** | typed request resize · north · deeper · 0.5 m → spatial engine: North bed 5.4 → 6.76 m², 1.64 m² kept out of the neighbouring beds, open centre and tree bed unchanged | not run |

What this shows and does not show: the rules have two real gaps on these sentences (A, D) and are already right on B
and C. The mock column proves that an answer of that shape goes safely through the checks into the same model and
engine, and that the checks correct a plausible over-reading (C). Whether a real model reads relationships better than
the rules is **not established here** — that is the live column.

## A structured reading and its validation record (case A, mock answer)

```json
{"kind": "description", "reading": "A 6 by 4 m yard with a tree in the northwest corner; the view to block comes over the north fence, and the middle stays open.",
 "description": {"dimensions": {"w": 6, "h": 4, "unit": "m", "evidence": "6 by 4 metres"},
  "trees": [{"side": "north", "corner": "northwest", "evidence": "an old maple in the northwest corner"}],
  "open_areas": [{"where": "centre", "reason": "open middle", "position_stated": true, "evidence": "Keep the middle open"}],
  "relations": [{"subject": "neighbours' kitchen window", "relation": "looks in over", "object": "the north fence", "evidence": "the neighbours' kitchen window looks in over the north fence"}, "…"],
  "values": [{"key": "privacy", "level": 2, "evidence": "I need privacy"}, {"key": "openness", "level": 2, "evidence": "Keep the middle open"}],
  "functions": [{"function": "z:screen", "where": "north-edge", "basis": "a view over the north fence into the yard → Screen on that edge", "evidence": "so I need privacy there", "alternative": false, "target_height_m": null, "year_round": "unstated"}], "…": "…"}}
```

| result | item | check |
|---|---|---|
| accepted | dimensions 6 × 4 m | both numbers were typed by the person |
| accepted | existing tree · northwest | quoted from the utterance; no coordinate is taken from the model — the workspace places it as an estimate |
| accepted | open space (open middle) | quoted; its extent is a suggestion until drawn |
| accepted | 3 relations | recorded as notes; they move no geometry |
| accepted | goals privacy, openness | quoted |
| accepted | z:screen → north-edge | a function of the knowledge graph, quoted; plants are chosen by the planting engine |
| accepted | constraint: keep the middle open | recorded with the brief |

## Not verified, or limited

- **The real model.** No call has been made. Prompt wording, effort level, latency, cost per sentence and — the question
  of this phase — whether it reads relationships better than the rules are all untested.
- The refusal-fallback request and the structured-output schema are accepted by the SDK and by the mock's contract
  checks; the real API's acceptance of this exact schema is unconfirmed until the first live call.
- Only a central open area is placed from words; an open area "on the east" is recorded as unknown and left to the tool.
- "Behind", "left", "right" name no compass side for the site in either reader; orientation stays the person's to give.
- The mock fixtures are seven sentences; other sentences come back as "nothing read" in mock mode.
- GitHub Pages stays offline-only; a hosted live demo needs a server that holds the key.
